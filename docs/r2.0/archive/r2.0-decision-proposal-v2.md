# R2.0 Decision Proposal — CourseStudio 产品目标与 D-01 至 D-12

> 本版本取代 `r2.0-decision-proposal-v1.md`；旧版存档于 [archive/r2.0-decision-proposal-v1.md](r2.0-decision-proposal-v1.md)。本文件仍是建议，不是批准记录。

- **编制日期**：2026-10-26
- **状态**：`PENDING_OWNER_APPROVAL`
- **适用范围**：CourseStudio 的课程生产架构、输出契约、自动化工具、质量控制与交付流程。
- **核心目标**：通过 Claude Code 和相关工具，稳定生产可分段制作、运行、录制、配音、拼接及复现的高质量视频课程。
- **审批规则**：本文提出的是决策建议，不是已批准记录。任何生产工具、课程内容、CI、Skill 或目录的实质变更，都应按相应阶段的授权执行。

---

## 0.0 核心原则：AI 多工具自检、`NEEDS_REVIEW` 与 owner 最终决定

1. **不设置强制人工审核门槛。** 工作流默认由 AI 完成内容、代码、视觉和交付自检；负责人只保留最终 `pass` / `reject` 权利，不需要逐项审核。
2. **生成与验证尽量分离。** 重要内容由不同模型、不同工具或不同验证机制复核；记录各自结果、证据和冲突。
3. **模型互相同意不等于事实已证实。** 事实优先回到原始来源，代码优先看实际执行结果，视觉优先看真实渲染画面；不能用“另一个模型也说对”升级证据状态。
4. **`NEEDS_REVIEW` 不等于必须人工审核。** 先自动返工、补充证据或换验证机制；只有需要负责人做取舍时，才升级给负责人。
5. **没有执行就不能报告通过。** 工具缺失、检查未运行、证据不足或检查冲突时，使用 `BLOCKED`、`PARTIAL`、`NEEDS_REVIEW`、`NOT_RUN` 等真实状态。
6. **最终交付由 AI 自检结果 + 证据 + 未验证事项组成。** 负责人可以直接接受，也可以 `pass`、要求返工或 `reject`。

## D-01 — 仓库拓扑

### 当前问题

现有文档、课程目录和脚手架对“课程是否属于根仓库”的描述存在不一致。仓库结构不应阻碍课程的稳定生产，也不能因为准备重构就直接删除旧成果。

### 建议决策

暂时使用单一根仓库，课程按稳定 ID 放置在 `courses/<course-id>/` 下。不立即采用 Git submodule，也不在这一阶段批量拆分现有课程。

### 理由

- 当前优先级是让生产链路可用，而不是提前优化仓库拆分。
- 单仓库便于统一管理模板、契约、Skill、测试和示例课程。
- 后续如课程数量、媒体体积或协作方式发生变化，再通过独立决策拆分仓库。

### 验证条件

- 新课程能通过统一脚手架创建。
- 课程与公共工具的依赖边界明确。
- 备份、CI、链接检查和课程选择逻辑使用一致的目录规则。
- 大型生成媒体和可重建产物有明确的跟踪策略。

**状态：** `PENDING_OWNER_APPROVAL`

## D-02 — HTML 课件与演示引擎

### 当前问题

现有 Reveal 和 Slidev 双轨设计有技术依据，但“同时维护两套引擎”本身并不等于产品能力。两套路线会增加模板、构建、浏览器验证和视觉规范的维护成本。

用户真正需要的是现代、清晰、适合录屏的演示页面，而不是特定框架。

### 建议决策

保留现有课件适配能力作为兼容路径。新课程在确定主路径前，使用同一段代表性内容验证候选路线，至少比较：

1. 全屏展示与画面比例；
2. 图形、公式、代码和复杂布局的表达能力；
3. 动画与口播的同步控制；
4. 逐页、逐段录屏的便利性；
5. 构建速度、运行稳定性和干净环境复现；
6. 修改一个页面后，是否会影响其他页面；
7. 浏览器截图、构建产物和 QA 证据的自动获取难度。

评估完成后确定新课程的默认路线，并保留必要的旧课程兼容能力。不得为了统一框架而批量转换旧课程。

### 验证条件

- 同一代表性内容在候选路线中有可运行样例。
- 有实际截图、构建结果和录制操作记录。
- 选择结果以成品效果、开发成本和维护成本为依据，而不是只依据版本新旧。

**状态：** `PENDING_OWNER_APPROVAL`

## D-03 — 动画引擎与片段生产

### 当前问题

用户需要的不是“能写动画代码”，而是可以表达概念、推导过程、图形变化和空间关系的动画。单个片段还必须方便独立渲染、返工和录制。

### 建议决策

Motion Canvas 作为优先验证路线；Manim 保留为按需启用的可选适配器，不作为所有课程的强制依赖。

每个动画片段应具有稳定 ID、明确的视觉目标、预期时长、依赖资源和运行入口。

建议每个片段至少明确：

- `segment_id`
- `learning_objective`
- `visual_intent`
- `duration_target`
- `animation_entry`
- `voiceover_ref`
- `slide_refs`
- `required_assets`
- `qa_requirements`

以上字段是建议的逻辑契约；正式字段名与 Schema 应在实现阶段统一。

### 验证条件

- 至少一个真实片段能够独立运行或渲染。
- 时长、帧数和帧率可以核对。
- 关键视觉变化符合片段设计。
- 修改该片段不会无意破坏其他片段。
- 引擎缺失时明确标记 `BLOCKED`，不将其报告为通过或不适用。

**状态：** `PENDING_OWNER_APPROVAL`

## D-04 — Claude Skills 与工具依赖管理

### 当前问题

依赖用户级 Skill、个人配置或本地路径的工作流，可能在当前机器上可用，却无法在新环境复现。

### 建议决策

对生产必需的 Skill 和工具固定版本、来源、许可证与校验信息。优先采用可审计的仓库内管理方式；如果许可或维护成本不允许 vendoring，则使用固定版本的外部依赖，并保留锁定清单。

不要为了满足“仓库里必须有文件”而复制不允许分发的 Skill。

### 验证条件

- 明确哪些 Skill 是生产必需，哪些是可选辅助。
- 记录来源、版本或 commit、许可证及哈希。
- 在干净配置下能够按说明安装或注册。
- 关键工作流不依赖未记录的用户级路径。
- 未安装的可选工具不会被误报为已经验证。

**状态：** `PENDING_OWNER_APPROVAL`

## D-05 — 研究主张与证据台账

### 当前问题

课程内容可能涉及论文、数据、公式、代码和外部事实。生成内容看似合理，不等于来源已证实。

当前 15 字段 Claim Ledger 具备较完整的字段设计，但不能仅凭字段集合一致，就认定真实课程迁移已经成功。

### 建议决策

将 15 字段 Claim Ledger v1 作为候选标准，保留旧格式只读兼容，先对真实样本执行迁移 dry-run。

每条重要主张应能追溯到来源和定位信息，并记录机器检查、独立验证与 `NEEDS_REVIEW` 状态；不以模型赞同替代原始来源。

AI 可以自动补充来源、定位和证据判定，但：

- 不能因为模型生成了引用，就将主张标记为已证实；
- 不能因为另一个模型表示赞同，就自动把证据升级为 `DIRECTLY_SUPPORTED`；
- 不能因为找到了相似文字，就自动认定来源支持当前主张；
- 不能在缺乏证据时自动填充审核状态或删除旧审核记录。

### 验证条件

- 完整 Schema 验证通过。
- 旧新格式映射可检查。
- 缺失来源、错误枚举和无效定位信息会失败或进入待审核状态。
- 真实样本逐条核对。
- 保留回滚路径。

**状态：** `PENDING_OWNER_APPROVAL`

## D-06 — 五维状态与交付门禁

### 当前问题

旧 QA 路径可能在构建跳过、运行时未验证的情况下仍输出 `PASS_VERIFIED`。这会使用户误以为课程已经可以交付。

### 建议决策

采用五个相互独立的状态维度：

| 维度 | 含义 |
|---|---|
| `STRUCTURAL` | 文件、结构、Schema、引用和基础契约 |
| `RUNTIME` | 动画、课件和相关运行路径 |
| `HUMAN` | 内容、视觉和教学质量的人工验收 |
| `RECORDING` | 录制媒体、音画对应、分段顺序和媒体检查 |
| `DELIVERY` | 最终交付包、证据完整性和复现条件 |

整体交付状态必须由明确规则派生，不允许静态检查通过后直接代表整个课程已完成。

建议的状态集合包括 `PASS`、`FAIL`、`BLOCKED`、`PARTIAL`、`NOT_RUN` 和 `NOT_APPLICABLE`。

### 验证条件

- 覆盖正常、缺文件、运行失败、证据缺失、人工未验收和豁免等边界情况。
- 运行时未执行时，不允许整体交付标为 `READY`。
- 人工验收未完成时，不允许声称成品质量已经确认。
- 每个状态都有来源、时间和对应证据。

**状态：** `PENDING_OWNER_APPROVAL`

## D-07 — 运行时、视觉与内容质量

### 当前问题

浏览器能打开、代码能编译、构建退出码为零，都不能证明课程达到了目标成品质量。

### 建议决策

建立四层质量控制：

1. **L1：结构与契约**——文件、Schema、引用、资源和命名。
2. **L2：真实运行**——动画构建/运行、课件加载、媒体和时长验证。
3. **L3：内容与视觉验收**——知识准确性、推导完整性、画面表达、口播同步、节奏和可读性。
4. **L4：交付与复现**——录制包、哈希、依赖锁定、干净环境重建和交付清单。

L3 必须明确人工检查范围。不能因为自动化测试通过，就自动认定课程的视觉设计或教学质量优秀。

### 验证条件

- 动画、课件和录制路径分别有实际执行证据。
- 代表性片段有预期效果和实际效果的对照。
- 重要事实、公式和数据有来源核验记录。
- 口播稿与片段和页面之间存在明确映射。
- 检查未执行、部分执行和失败都有不同状态。

**状态：** `PENDING_OWNER_APPROVAL`

## D-08 — 数据、课程与备份处置

### 当前问题

重构或重置可能影响已有课程、研究成果、媒体、工具和本地配置。仓库外备份有助于降低风险，但哈希一致和抽样恢复不等于完整恢复演练已经完成。

### 建议决策

在任何删除、归档、批量迁移或覆盖之前：

1. 核对备份清单与排除项；
2. 确认关键成果存在于独立副本；
3. 明确依赖、密钥和外部服务等不能简单由源文件恢复的部分；
4. 对重要恢复路径执行实际演练；
5. 单独批准不可逆操作。

当前报告所述 primary/secondary 双副本及其哈希结果可以作为已执行工作的证据，但仍需区分“文件一致”“抽样恢复通过”和“完整恢复通过”。

**状态：** `PENDING_OWNER_APPROVAL`

## D-09 — CI 与测试策略

### 当前问题

只运行 Python 语法检查、契约测试和链接检查，无法证明真实课程能够构建、运行和交付。

但每次改动都执行全部渲染、浏览器和媒体测试，也可能带来过高成本。

### 建议决策

- **L1：** 每次相关变更执行结构、契约、单元和链接检查。
- **L2：** 对实际受影响的动画、课件或录制组件执行对应集成检查。
- **L3：** 对代表性成品执行人工内容与视觉验收。
- **L4：** 独立执行干净环境复现，检查依赖、安装和交付说明。

L1/L2 的路径规则必须明确；完整 clean-room 测试可以单独安排，但不能替代当前变更所需的测试。

### 验证条件

- 错误 fixture 能让对应测试失败。
- 修改动画时会触发动画检查。
- 修改课件时会触发对应的课件检查。
- 修改公共契约时会验证实际消费者。
- CI 的成功不会覆盖课程自身未完成的人工验收或录制状态。

**状态：** `PENDING_OWNER_APPROVAL`

## D-10 — 命名、片段与产物追溯

### 当前问题

如果研究资料、口播稿、课件、动画和录制片段使用互不相关的名称，后续修改就很难判断哪些产物需要同步更新。

### 建议决策

新课程使用稳定的课程 ID 和片段 ID。课程、章节、片段、动画、页面、口播稿、来源和录制文件之间应有明确的引用关系。

不要仅依靠文件名或人工记忆建立关联。

### 验证条件

- 每个片段可定位到对应脚本、动画和课件。
- 每个录制文件可追溯到来源片段。
- 删除或更名资源时，引用检查能够发现断链。
- 旧课程可通过例外映射继续工作，不要求一次性改名。

**状态：** `PENDING_OWNER_APPROVAL`

## D-11 — Trace 报告是否单独持久化

### 建议决策

优先从研究主张、片段、课件、录制和 QA 数据派生 `trace-report.json`，避免维护重复事实源。

如果后续确实需要独立存储审计事件，再单独定义事件模型与保留策略。

### 限制

派生报告必须保留来源引用、生成时间和输入版本。不能把派生报告本身当作原始证据。

**状态：** `PROPOSED_DESIGN_DECISION`，仍须核对现有 R1 记录，不应仅凭本文声称此前已完成审批。

## D-12 — 最终课程成品与输出契约

### 当前问题

当前架构容易从目录、Schema、工具版本和测试流程出发定义系统，却没有先把最终交付物及其质量标准完整固定下来。

这会造成一种情况：测试通过、文件齐全、状态完整，但产出的课程仍然不符合实际制作需求。

### 建议决策

将以下内容定义为 CourseStudio 的标准交付对象。

#### A. 课程蓝图

- 目标受众、前置知识和学习目标；
- 章节顺序与知识依赖；
- 每段的教学目标、核心结论和预期视觉表达；
- 预计时长及需要人工决定的内容。

#### B. 动画与课件

- 可复现的动画源代码和运行入口；
- 可全屏展示的 HTML 或等效演示页面；
- 公式、图形、数据、代码和关键视觉元素；
- 片段级输入、输出、资源引用和时长信息；
- 实际运行与构建证据。

#### C. 口播稿与同步关系

- 可直接用于配音或录制的口播稿；
- 每段口播与片段 ID、页面 ID 的对应关系；
- 必要的停顿、强调、转场和录制提示；
- 画面与讲解不一致时的明确待办。

#### D. 支撑材料

- 研究来源与定位；
- 关键主张、公式和数据的核验记录；
- 外部素材的来源和许可信息；
- 未解决的问题与人工审核清单。

#### E. 录制与交付包

- 片段顺序和拼接清单；
- 录屏、配音和媒体处理说明；
- 录制文件与最终文件的清单和哈希；
- 交付状态及未完成事项。

#### F. 质量与审计报告

- L1/L2/L3/L4 检查结果；
- 实际执行命令、退出码和工具版本；
- 输入文件和输出文件的可追溯关系；
- 已通过、失败、阻塞、未运行和不适用的明确区分；
- 人工验收范围、审核结果及剩余风险。

### 验证条件

选择一个具有代表性的真实课程章节，完整走通从研究到交付的流程。

必须实际检查：

1. 成品是否能表达预定知识，而不只是生成了一堆文件；
2. 动画与课件是否可运行；
3. 口播与画面是否对应；
4. 研究来源是否可追溯；
5. 片段能否独立返工；

### 阶段 C：验证契约与只读兼容

- 使用完整 JSON Schema Draft 2020-12 验证器。

### 阶段 D：真实课程生产试跑

- 选择一个有代表性的章节。
- 运行研究、脚本、课件、动画、口播和交付流程。

- 再考虑旧课程迁移、批量内容修复和历史目录归档。
